# パートナーの共有 ToDo が消える・届かない不具合の修正（Build 9）

2026-10-28。ブランチ `fix-partner-shared-item-sync`（main の `8c6300c` から）。main にはまだ入れていません。
Firebase（Functions・Firestore のルール・索引・Hosting）への公開、TestFlight へのアップロード、Firebase Console・Apple Developer の変更はしていません。

## 実機で起きたこと（池上さんの報告）

環境：TestFlight 1.0（8）、2人とも同じわが家に参加済み、Build 8 のルール・Functions を本番に公開済み、APNs 認証キー登録済み、両方の iPhone で通知を許可済み。

1. パートナーの iPhone で共有 ToDo を追加する
2. 追加した ToDo が、パートナーの画面から消える
3. オーナーの画面に出ない
4. オーナーにプッシュ通知も届かない

## 調べたこと

Build 7（`319ce63`）と Build 8（`7557637`）を比べ、次を確かめました。

| # | 確かめたこと | 結果 |
| --- | --- | --- |
| 1 | Build 8 のルールが、パートナー（role=`member`）の共有項目の作成・更新を断っていないか | **断っていない**。Build 8 でルールを変えたのは端末の文書（`users/{uid}/devices`）だけ。共有項目のルールに役割（owner／member）の区別は無い。Mac の Rules Emulator（61件成功）で、パートナー（bob）の作成・更新が通ることも確かめられている |
| 2 | `createdBy`・`updatedBy` に操作した本人の UID が入るか | 入る。Firestore の窓口が、その端末でサインインしている人の UID を入れる。担当（`assigneeUID`）は常に null。groupID はサーバーが返したわが家、itemID は項目の UUID |
| 3 | オーナーの UID を固定で使っていないか | 使っていない（アプリはオーナーの UID を知らない） |
| 4 | パートナーの認証の UID と、メンバー文書の UID が一致するか | サーバーの参加の処理（`acceptInvite`）は `groups/{groupID}/members/{本人の UID}` を作る。ルールも同じ場所を見る。コードの上では一致する |
| 5 | 書き込みに失敗したとき、項目を消していないか | データは消していなかった。断られた作成は「自分だけ」の項目として端末に移していた。**ただし、そのことを画面に一切出していなかった**（下の原因1） |
| 6 | 最初の一覧・一時的な空の一覧で、未送信の項目を消していないか | **消すことがあった**（下の原因2） |
| 7 | App Check・Authentication・Firestore のエラーを握りつぶしていないか | **握りつぶしていた**。権限・サインイン以外はすべて「そのほか」にまとめ、理由を画面にも出していなかった（下の原因3） |
| 8 | `MainTabView`・`AppState`・やること画面・共有同期に Build 8 の変更による不具合が無いか | 無い。Build 8 の変更は通知の登録と、通知をタップしたときの画面の移動だけで、共有項目の保存の処理は Build 7 のまま |
| 9 | 通知 | `onSharedItemWritten` は、サーバーに保存できた書き込みでだけ動く。今回は保存が断られていたので、通知が届かないのは当然の結果（通知の経路の問題より先に、保存の失敗がある） |
| 10 | 端末の文書の場所 | それぞれの人の `users/{自分の UID}/devices/{インストールごとの ID}`。サインインの情報から場所を決めるので、相手の UID の下には書かない |

## 原因

### アプリのコードで特定できた原因（Build 7 から。Build 8 の変更による不具合ではない）

1. **共有の保存が断られたことを、画面に出していなかった**
   - `LifeOS/Core/Sharing/HouseholdItems.swift`（`8c6300c` の 271行目・279行目）：`notice = failure.message` でお知らせを作っていたが、どの画面もこの `notice` を表示していなかった
   - 断られた項目は、`LifeOS/Core/Store/LifeStore.swift`（433行目）`items.append(Self.personalCopy(item))` で「自分だけ」の項目に移っていた。共有マークが消え、「共有」の絞り込みからも外れるため、**利用者からは「消えた」ように見えた**
2. **最初の一覧・一時的な空の一覧で、送信待ちの項目を画面から消すことがあった**
   - `LifeStore.swift`（418行目）`householdItems = snapshots.map(\.item)`：Firestore から届いた一覧で丸ごと入れ替えていたため、保存の結果が出る前に空・古い一覧が届くと、送信待ちの項目が一度画面から消えた
3. **失敗の理由が分からなかった**
   - `LifeOS/Core/Sharing/FirestoreSharedItemsBackend.swift`（105行目）`default: return .other`：権限（7）とサインイン（16）以外は、通信できない場合も含めて「そのほか」にまとめていた。読み取りの見張りが止まっても、画面には何も出ていなかった

### サーバーが保存を断った理由について

- このリポジトリのルールでは、パートナーの作成・更新は許されています。Mac の Rules Emulator の既存のテスト（bob＝パートナーが作成・更新）も成功しています。今回、オーナーとパートナーの両方について、ToDo・買い物の作成・更新のテストを足しました
- したがって、実機で断られた理由は、**リポジトリのコードからは1つに決められません**。推測で直すことはしていません。考えられるのは次のどれかです：
  - 本番に公開されているルールが、リポジトリの `firestore.rules` と違う（別のフォルダから公開した など）
  - パートナーの iPhone で、サインインの情報（ID トークン）を新しくできない（Authentication の App Check の強制適用は有効。トークンを新しくできないと、Firestore からは「サインインしていない人」に見える）
  - 本番のデータが想定と違う（パートナーのメンバー文書・わが家の「共有する種類」）
- Build 9 では、これを実機で確かめられるように「わが家の設定 → 共有の状態を確かめる」を追加しました（下）。Build 9 を入れたパートナーの iPhone で押すと、どこで止まっているかが分かります

## 影響範囲

- 共有 ToDo・買い物の作成・名前の変更・完了などが、サーバーに断られた場合のすべて（オーナー・パートナーとも同じ処理。Build 7・Build 8）
- 断られた作成は、データとしては端末に「自分だけ」の項目で残っている（消えてはいない）。サーバーには保存されていないので、相手にも通知にも届いていない
- 端末の個人データ・わが家・ほかの共有項目への影響は無い

## 修正内容（Build 9）

### Swift（アプリ）

- 共有の保存が断られたら、画面の上に「**共有できなかったため、自分だけに保存しました（理由）**」を出す（`SharedSyncNoticeBanner`。`MainTabView` の上に重ねる。閉じられる）
  - 理由：権限がありません／サインインの確認ができません／通信できません／原因が分かりません（エラーの文・UID は出さない）
  - 変更・削除が断られたときは「共有の変更（削除）を保存できませんでした（理由）」
- 項目は消さず、「自分だけ」の項目として端末に残す（これまでどおり）。同じ項目を2つ作らない
- 保存の結果が出るまで、送信待ちの共有項目を覚えておき、空・古い一覧が届いても画面から消さない（`pendingHouseholdCreates`）
- 失敗の理由を分ける：権限（7）・サインイン（16）・通信（14・4）・そのほか。最近の失敗の理由を「わが家の設定」に出す
- 「わが家の設定 → 共有の状態 → 共有の状態を確かめる」を追加（読み取りだけ。書き込みはしない）：
  - サインイン／サインインの更新（ID トークンを新しくできるか）／わが家の読み取り／自分のメンバー文書／共有項目の読み取り／サーバーの共有する種類
  - 結果は「OK」「失敗（コード 7）」「見つかりません」の形だけ（UID・トークン・エラーの文は出さない・保存しない）
- オーナーとパートナーは、これまでどおり同じ処理で保存する（役割で分ける処理は無い）

### Firestore のルール

- **変更なし**。オーナー・パートナーの両方の作成・更新、作成者・更新者のなりすましの拒否、メンバーでない人の拒否、端末の登録のあとも権限が変わらないこと、断られた書き込みが保存されないことのテストを追加

### Functions

- **変更なし**。パートナー → オーナー、オーナー → パートナーの通知、本人を除く、通知 OFF・内容の表示のオン／オフ、保存されていない項目では何も作らないことのテストを追加

## 既存データへの影響・Build 8 の利用者への対応

- 消えたように見えた ToDo・買い物は、その iPhone の「自分」の中に残っています（「すべて」または「自分」の絞り込みで見えます）
- 原因が分かって直ったあと、その項目を長押し →「編集」→「わが家で共有」にすると、同じ項目のまま共有されます（2つにはなりません）
- サーバー・わが家・ほかの人のデータは変えていません。消す作業もありません

## 本番のルール・Functions の更新は必要か

- この修正のためのルール・Functions の変更は **ありません**（アプリの Build 9 だけ）
- ただし、本番に公開されているルールがリポジトリと同じかは、池上さんが Firebase Console → Firestore Database →「ルール」で確かめてください。次の言葉が入っていれば Build 8 のルールです：`kindIsEnabled`、`schemaVersion`、`deviceID.matches`
- 違っていたら、main の `firestore.rules` を `firebase deploy --only firestore:rules` で公開し直すと直る見込みです（公開は許可のあとで）

## Build 9 の2台での確認（A：オーナー、B：パートナー）

Build 9 を TestFlight で2台に入れてから行います。

1. B：わが家の設定 →「共有の状態を確かめる」→ 結果をメモする（全部「OK」で、共有する種類に ToDo・買い物が出るか）
   - 「サインインの更新：失敗」→ サインインの情報を新しくできない（App Check・Authentication 側）
   - 「わが家の読み取り」「共有項目の読み取り」が「失敗（コード 7）」→ ルールかメンバーの登録の問題
   - 「メンバーの登録：見つかりません」→ メンバー文書が無い
2. A も同じく確かめる
3. B：「わが家で共有」で ToDo を追加 → B の画面に共有マーク付きで残る → A に出る → A に通知が届く（B には届かない）
4. A：「わが家で共有」で買い物を追加 → B に出る → B に通知
5. B が A の項目の名前を変える → A に出る・A に通知。A が B の項目の名前を変える → B に出る・B に通知
6. 共有が断られたとき：画面の上に「共有できなかったため、自分だけに保存しました（理由）」が出て、項目は「自分」に残る。その理由と、手順1の結果を記録する
7. 機内モードで共有の ToDo を追加 → 画面から消えない → 機内モードを切ると A に出る（1件だけ）
