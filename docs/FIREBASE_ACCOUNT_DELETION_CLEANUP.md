# アカウント削除のあとの Firestore の整理

作業用ブランチ：`firebase-account-deletion-cleanup`（main `c0c554f` から作成。**main にはまだ入れていない**）

**本番の Firebase（Firestore・Functions・Hosting・Console）には何も送っていない・変えていない。**

## 何を作ったか

アプリで「アカウントを削除」すると、Firebase Authentication からその人が消えます。
そのあと **サーバー（Cloud Functions）が自動で** その人の Firestore の情報を整理する仕組みを作りました。

- 新しい Function：`onAuthUserDeleted`（`firebase/functions/index.js`）
  - Firebase の **安定版の「利用者が削除されたら動く」仕組み**（第1世代の `auth.user().onDelete`）を使う
  - 第2世代（いまの招待・通知の Function）には、利用者の削除で動く仕組みが無いため、これだけ第1世代。同じプロジェクトで一緒に使える
  - プレビュー版の仕組みは使っていない
- 整理の中身：`firebase/functions/src/accountCleanup.js`（何をするか決める部分）・`src/accountCleanupRunner.js`（実際に Firestore を整理する部分）

## なぜ必要か

これまでは Authentication の利用者を消しても、Firestore には次が残るおそれがありました。

- 生活グループのメンバー情報（消えた人がメンバーのまま見える）
- 端末トークン（消えた人の iPhone に通知が届き続けるおそれ）
- 消えた人が担当の共有項目（ルール上「担当はメンバーだけ」なので、その項目をアプリから更新できなくなる）
- owner が消えたグループ（owner がいなくなる）、誰もいないグループ（誰も読めないのに残る）

いまは Firestore に生活データがないので実際の影響はありませんが、共有を始める前に用意しておきます。

## 削除される情報と残る情報

| 情報 | どうなるか |
| --- | --- |
| `users/{uid}`（表示名など） | 消える |
| `users/{uid}/devices`（端末トークン）など、`users/{uid}` の下すべて | 消える |
| `groups/{g}/members/{uid}`（その人のメンバー情報） | 消える（すべての所属グループで） |
| その人が担当の共有項目 | **項目は残る**。担当だけ `null`（なし）になる。退出したグループに残っていた分も |
| 共有項目の作成者・更新者の記録（`createdBy`・`updatedBy`） | 残る（履歴として） |
| パートナーが残っているグループと、その共有項目 | **残る**（消さない） |
| `groups/{g}.createdBy`（グループを作った人の記録） | 残る（変えない） |
| 誰も残らない生活グループ | `items`・`members`・`notificationLog` など下のすべてを含めて消える |
| その人が作った・使った招待、消したグループの招待 | 消える（消えた人の名前で、まだ使える招待を残さない） |
| ほかの人の端末・グループ・共有データ・招待 | 触れない |

## owner が削除されたときの引き継ぎ

1. 残っているメンバーのうち、**参加（`joinedAt`）がいちばん古い人** が新しい owner になる
2. 同じ時刻なら、**UID の文字の並び順** で先の人（毎回同じ結果になる。言語の設定などに左右されない並べ方）
3. 新しい owner への変更と、削除された人のメンバー情報の削除は、**同じトランザクション（まとめて一度に行う書き込み）** で行う。片方だけになることはない
4. グループの `updatedAt` はサーバーの時刻にする。`createdBy` は変えない
5. ほかにも owner がいる場合は引き継がず、削除された人を外すだけ
6. ほかに誰もいない場合は、グループを丸ごと消す
7. 引き継ぎは、グループの文書（`groups/{groupID}`）が在るときだけ。文書がもう無いグループは、途中まで削除されたグループとして下まで丸ごと消す（下の「途中で失敗したとき・やり直し」）

一般メンバーが最後の一人だった場合（owner が先に退出していたなど）も、誰も読めないグループを残さないため、丸ごと消します。

## 所属グループの探し方（メンバー検索）

- メンバー文書に **`uid`（文書の ID と同じ本人の UID）** を追加し、Firestore の **collection group 検索**（すべての `members` を1回の検索で横断）で、その人の所属を探す
- 全グループを1つずつ調べる総当たりはしない
- 担当の項目も同じく、すべての `items` を `assigneeUID` で1回の検索で探す
- 安全のため：
  - Firestore のルールで、`uid` は **文書 ID と同じ本人の UID だけ** 書ける（別人の UID は書けない）。更新は誰にもできないので、あとから変えることもできない
  - 整理では、見つかった文書の **ID と `uid` の両方が本人** のものだけを扱う
  - `acceptInvite`（招待で参加）も `uid` を入れる
- 索引（`firestore.indexes.json`）に、`members.uid` と `items.assigneeUID` の collection group 用の索引を追加（本番に送るときに一緒に作られる。Emulator は索引なしでも動く）
- **これまでのデータの移し替えは不要**：本番の Firestore にはまだ共有データが無い（ルールも全拒否）ため、`uid` の無い古いメンバー文書は存在しない

この方法を選んだ理由：Firebase が用意している標準の検索だけで済み、仕組みが単純で、グループの数が増えても遅くならない。本人以外の UID を書けないことをルールとテストで保証できる。

## 処理は非同期

- アプリの「アカウントを削除」は、これまでどおり **Apple で再認証 → Apple の連携を解除 → Firebase の利用者を削除** の順（**アプリは変えていない**）
- Firestore の整理は、そのあと **サーバーで自動に**（数秒〜数十秒ほどあとに）行われる。アプリは整理が終わるのを待たない

## 途中で失敗したとき・やり直し

- Firestore の削除は、全部をまとめて一度に行うことができない（途中で止まることがある）ことを前提にしている
- 整理を始めるとき、整理するグループの ID を作業の記録（`accountDeletions/{uid}`）に残し、**すべて終わってから** 記録を消す。途中で止まっても、次の実行で記録を見て続きができる
- 失敗したときはエラーにして、Firebase に **自動でやり直してもらう**（`failurePolicy`）
- **何度実行しても同じ結果** になる：すでに消えているものは飛ばし、済んだグループには触れない。同じ削除のイベントが2回届いても、同時に届いても壊れない
- 作業の記録はアプリから読み書きできない（ルールで拒否）。中身はグループの ID と時刻だけ
- **グループの文書（`groups/{groupID}`）がもう無いグループは「途中まで削除されたグループ」として、下に残っているものを最後まで消す**。
  丸ごと削除の途中で止まると、グループの文書は消えたのに、パートナーのメンバー文書・items・notificationLog などが残ることがある。
  このとき、残っているメンバーの人数や役割にかかわらず、`groups/{groupID}` の下をすべて消す（owner の引き継ぎはしない。引き継ぎはグループの文書が在るときだけ）。
  削除された人のメンバー文書がもう無くても、作業の記録に残したグループ ID から見つけて、やり直しで消せる。何度やり直しても成功し、ほかの正常なグループには触れない
- 共有項目の通知の Function は、グループがもう無いときに通知の記録を作らないようにした（整理のあとに、消したグループの下に記録が残らないように）

## プライバシー：ログに出さないもの

ログ（Firebase のログ）に出すのは **UID と件数だけ**（例：外したメンバーの数、引き継いだ数、消したグループの数）。

- 出さない：メールアドレス、Apple の情報、表示名、電話番号、端末トークン、予定やリストなど生活の内容
- 失敗したときも、エラーの種類（コード）と UID だけを出す。元のエラーの文章は出さない
- テストで、削除トリガーのコードにこれらの項目名が無いことを確かめている

### Mac での実行手順（Node 22 で）

（もう一度確かめるときの手順）

`package.json` の指定どおり **Node 22** で実行します（本番の Cloud Functions と同じ版。いまの Mac の Node 24 のままでは実行しない）。

1. Node 22 に切り替える（どちらか）
   - Homebrew を使っている場合：
     ```
     brew install node@22
     export PATH="$(brew --prefix node@22)/bin:$PATH"
     ```
     （`export` の行は、このターミナルの窓の中だけで有効。窓を閉じると元の Node 24 に戻る）
   - Homebrew が無い場合：https://nodejs.org/dist/latest-v22.x/ から `node-v22.…​.pkg` を入れる（Mac 全体が Node 22 になる。あとで Node 24 に戻すときは、Node 24 の .pkg を入れ直す）
2. `node -v` で `v22.…` と出ることを確かめる
3. GitHub でブランチ `firebase-account-deletion-cleanup` を選び、ZIP でダウンロードして展開する
4. ターミナルで、展開したフォルダの `firebase/functions` に移動する（例：`cd ~/Downloads/life-os-firebase-account-deletion-cleanup/firebase/functions`）
5. `npm install`（新しく展開したフォルダなので、Node 22 で入れ直しになる）
6. `npm test`
7. 3種類が順に動く。Functions は2つのファイルに分かれて続けて動く。目安：単体 `# tests 47`、Rules `# tests 38`、Functions `# tests 14` と `# tests 16`（合計115件）。それぞれ `# fail 0` なら成功
8. 失敗したら、出てきた文をそのまま送ってください（`PERMISSION_DENIED` の表示は、拒否を確かめるテストで出る想定どおりのもの）

## 残っているリスク・次に決めること

- Node 22 は 2027-10-31 に Google Cloud での提供終了の予定。それまでに次の版へ上げる
- 自分で退出した人が担当の項目は、その人がアカウントを消すまで担当が残る（その項目をアプリから更新するには担当を変える必要がある）。退出のときの扱いは、退出の画面を作るときに決める
